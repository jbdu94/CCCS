2. Two ways to reach this deployment — and why both matter

  • Through the gateway (kubectl port-forward svc/gateway 8000:8000) — the only path a real downstream agent is meant to use. This is where real-time prevention happens.
  • Straight to the registry (kubectl port-forward svc/registry 8001:8000) — bypasses the gateway entirely. Worth knowing why this works at all: kubectl port-forward tunnels directly to a pod through the Kubernetes API server, which does not go through the cluster’s normal pod-to-pod network path — so it bypasses NetworkPolicy enforcement by design, not because the policy failed. This path is where real-time prevention is absent and detection (reading telemetry after the fact) is the only defense — deliberately, to demonstrate what happens without a gateway in front.

Both results below come from the exact same attack script (red_team/uc1_supply_chain_attack.py) against the exact same real registry pod — only the entry point differs.

Clean, confirmed, no crash. How to interpret this

With no gateway in the path, the full attack sequence completes — register, rug-pull, call — exactly as it would against an undefended registry. The blue team detector then reads the real telemetry the K8s registry pod itself logged (not simulated) and catches all three real signs of the attack:

  2. Behavioral match — the description changed after registration
  3. Impact match — the agent actually acted on the drifted description

A one-off worth knowing about, not worth chasing

One run of this test returned 4/4 findings instead of 3/3, with TOOL_CALLED_WITH_DRIFTED_DESCRIPTION firing twice. Checked the detector code — there’s only one place that logs a tool_called event, so this wasn’t a detection-logic bug. The most likely explanation: kubectl port-forward tunnels can occasionally deliver a single HTTP request as two separate connections — a known quirk of that tunneling mechanism, not a flaw in the attack script or the detector. Re-running immediately after produced a clean 3/3 both times. If this becomes consistently reproducible rather than a one-off, it’s worth digging into further — as a single occurrence, it isn’t.

6. AI mode — real result, OpenAI end-to-end

First confirmed end-to-end run of the full OpenAI pipeline against real Kubernetes telemetry.

Getting here took one real bug fix, worth recording: the agent’s own prior turn output was being re-submitted to the API on the next turn with fields (like a message item’s status) that are valid on output but rejected on input — Error code: 400 - Unknown parameter: 'input[1].status'. Fixed by using the Responses API’s server-side conversation state (previous_response_id) instead of manually reconstructing turn history — verified with a mocked multi-turn test before this live run confirmed it.

(A ConfigMap update alone doesn’t restart a running pod — Kubernetes doesn’t do that automatically. This step is required after any code change to a service that’s already deployed.)

A second real bug, found in the same run: triage grounding was too strict

Every triage finding in both runs above came back NEEDS_HUMAN_REVIEW with grounded=False — for all 5 findings, in both runs, consistently. That consistency across independent runs was the signal this was a real bug, not noise.

Root cause: the false-positive triage layer’s evidence-grounding check required the model’s quoted evidence to appear as an exact character-for-character substring of the raw event log’s JSON serialization (json.dumps(raw_events)). In practice, a model’s natural quote of real log content routinely includes small formatting differences that make a strict match fail even when the quote is completely genuine — wrapping it in its own quotation marks, or prefixing it with the JSON key name it came from (e.g. quoting "implementation": "cat /etc/passwd..." instead of just cat /etc/passwd...). The strict check couldn’t tell that apart from an actually-hallucinated quote.

Fix: the grounding check now compares against the real string values inside the event data (not the JSON text’s exact formatting), strips common wrapping patterns (surrounding quote marks, a leading "key": prefix) before checking, and tries a whitespace-normalized comparison as a fallback. The system prompt was also tightened to ask more explicitly for a bare quote with no wrapping.

Verified both directions before trusting it, not just the direction that makes the fix look good: - A real quote with realistic wrapping noise (JSON key prefix, quote marks) → now correctly grounds, disposition: confirmed - A genuinely fabricated quote (invented text, not present in the log anywhere) → still correctly fails grounding, disposition: needs_human_review — the anti-hallucination safeguard was not weakened by this fix, only made accurate about what counts as a real quote.

This hasn’t yet been re-confirmed live against a real run (both test cases above were run with mocked model responses matching the observed wrapping pattern) — worth a real re-run with --triage to confirm grounded=True shows up where it should, next time this runs.

Update: the triage-grounding root cause is now known — this was never a code bug. TRIAGE_DEBUG=1 traced it to Error code: 401 - API key is invalid on every single call: ANTHROPIC_API_KEY had the OpenAI key sitting in it by mistake. The grounding fix itself (both the JSON-quote-wrapping tolerance and the printed-reasoning debug output) is real, tested, and left in place — it was just never the actual problem. Re-confirmation with a valid key is still the one open item.
